# Operator request

- Evaluate whether VoxVulgi should move from SQLite to SurrealDB because the product has multiple parallel lanes, SurrealDB can be embedded, and its query engine is implemented in Rust.
- Turn that evaluation into a detailed no-context work packet while preserving all previously planned freeze, startup, database-access, and observability remediation.
- Do not treat a database change as a remedy for the current incident unless exact evidence proves that relationship.

# Verified current VoxVulgi database state

- The canonical product database is `<app-data>/db/app.sqlite`; it is local rather than on the NAS.
- One 2026-08-23 checkpoint inspection snapshot measured the main file at 1,106,968,576 bytes, schema version 54, 67 application tables, 77 named indexes, 24 active triggers, and 47 foreign-key entries. This is captured-snapshot evidence, not a timeless live byte count: a later same-day live observation measured 1,107,058,688 bytes plus an 8,272-byte WAL. Every benchmark source must record acquisition time, backup/checkpoint identity, main/WAL/SHM sizes, and hashes after a consistent backup/close boundary.
- `product/engine/src/db.rs` defines `CURRENT_SCHEMA_VERSION=54` and 46 explicit migration steps.
- The job runner has nine tracks and up to ten default worker slots. Immediate transactions protect canonical job claims and identity ownership.
- Triggers enforce provider-install authority, publication legality, rollup dirtiness, and other product invariants. Existing backups, repairs, watcher probes, scripts, and tests encode SQLite-specific behavior.
- Runtime engine code still contains hundreds of direct `db::open`, `db::open_readonly`, and `db::migrate` calls and concrete rusqlite transaction parameters. There is no database-engine adapter today.
- WP-0310 has already fixed database-first startup ordering. WP-0312 will create the production `AppDatabase`/`DatabaseRuntime` access boundary, bounded reader/writer admission, operation registry, and lock attribution while retaining SQLite.
- One v0.1.179 trace contains an app-side `database is locked` error and its watcher contains nine database-probe timeouts. The lock holder remains unknown, and the evidence does not prove SQLite caused the native-window freeze.
- A historical v0.1.169 run against a then-1,066,110,976-byte canonical database recorded an 85-ms Options-to-Media-Library render and a 3,105-ms asynchronous query. The run is invalidated for current-profile/non-mutation closure because an agent-controlled headless process was launched against canonical operator app data. Its timings are hypothesis context only and cannot serve as the exact SQLite baseline or any WP-0315 decision cell. A fresh verified closed backup/clone and safe baseline run are required. The current database is not globally proven too slow; individual queries and concurrency paths require measurement.
- Subscription lists, playlists, library metadata, job history, and user media are irreplaceable. Third-party 4KVDP SQLite databases/exports remain read-only and are not migration inputs.

# Verified SurrealDB candidate state as of 2026-08-23

- SurrealDB's latest stable release line is 3.2 and latest patch is 3.2.4, released 2026-08-03: `https://surrealdb.com/releases/3.2`.
- The official Rust embedding guide supports in-process `Surreal::new::<RocksDb>(path)` with the `kv-rocksdb` feature: `https://surrealdb.com/docs/reference/rust/embedding`.
- Embedded mode removes a separate database server/network hop but does not remove storage-engine scheduling, compaction, cache, transaction-conflict, backup, and lifecycle concerns.
- Official SurrealDB Rust SDK documentation states MSRV Rust 1.89+, so the observed local rustc 1.91.1 nominally satisfies that public floor. Separately, SurrealDB 3.2.4's contributor workspace pins Rust 1.95 and uses edition 2024, while VoxVulgi's desktop crate uses edition 2021; a 2021 parent may consume a 2024 dependency, so neither upstream fact proves VoxVulgi must change edition or toolchain. Only the exact Windows MSVC/Tauri `surrealdb=3.2.4` + `kv-rocksdb` clean compile/link proves compatibility.
- SurrealDB 3.2.4 depends on `surrealdb-rocksdb`; RocksDB is a C++ storage engine. The candidate has a Rust query/database layer but is not an all-Rust persistence stack.
- RocksDB's official operations documentation states that a primary read-write database is normally opened by one process at a time and is safely shared by threads through one DB object. Its FAQ documents secondary and multi-process read-only modes, but whether SurrealDB's embedded/query layer exposes a supported, compatible path for VoxVulgi diagnostics is unproven. The current external tools that directly open live SQLite therefore create a required compatibility experiment, not a predetermined incompatibility: `https://github.com/facebook/rocksdb/wiki/Basic-Operations` and `https://github.com/facebook/rocksdb/wiki/RocksDB-FAQ`.
- SurrealKV 0.21.2 is beta according to current SurrealDB storage guidance, and its own tagged README says Windows file operations are not thread safe (`TODO`) with reduced functionality/performance. It is excluded from a production Windows candidate until both conditions change: `https://github.com/surrealdb/surrealkv/blob/v0.21.2/README.md`.
- SurrealDB supplies schema, transaction, full-text search, export/import, and upgrade facilities, but equivalence with VoxVulgi's exact SQLite triggers, current `instr(lower(...))` search semantics, specified-but-not-yet-shipped FTS5 direction, migrations, repair tools, and backup contract is not proven. Current inspection found no SQLite FTS virtual table; FTS must be scored as a separately labelled forward-looking cell rather than misrepresented as current-engine parity.

# Authority and packet boundaries

- WP-0312 is a hard predecessor to the decision benchmark. Comparing a tuned new engine against the current unbounded/direct-access topology would measure architecture cleanup plus engine replacement and would not answer the database question.
- WP-0298 and WP-0311 through WP-0314 retain ownership of current freeze remediation. WP-0315 must not block, replace, or claim to solve them.
- WP-0310 database-first startup, user-data preservation, offline installer, portability, proof standard, and third-party read-only policies remain mandatory.
- This packet authorizes only an isolated shadow importer, benchmark harness, compatibility/recovery experiments, and a decision record. It does not authorize production dual-write, production schema changes, canonical database conversion, or a user migration.
- A `candidate_for_operator_decision` result is not authority to migrate. Production adoption requires a separate operator-approved refinement/work packet and specification/design update with staged import, rollback, release, updater, support, and user-data proof.

# Decision rubric

- Outcomes are exactly `reject`, `defer`, or `candidate_for_operator_decision`.
- Apply outcomes in this exact precedence. First, any observed correctness/invariant/data-loss/unrecoverable-recovery failure, rejected distribution/license decision, unsupported exact Windows/Tauri build, failed full-offline installer, failed backup/restore, failed diagnostics/app-dead observability gate, or measured breach of any frozen numeric resource/recovery budget yields `reject`, even if other evidence is missing. Second, if no reject condition exists, missing exact-source data, excessive variance, incomplete operation coverage, unaligned durability, unresolved distribution/license acceptance, a missing resource/recovery budget, or an incomplete external dependency/proof cell yields `defer`. Third, only a complete run with neither condition may be evaluated for `candidate_for_operator_decision`; a complete run that fails its selected material-benefit branch yields `reject`.
